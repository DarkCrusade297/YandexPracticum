# 📅 Event Manager System - Event Controller
- GET /events - получение списка всех мероприятий
- POST /events - создание мероприятия
- GET /events/{id} - получение мероприятия по его уникальному идентификатору
- PUT /events/{id} - изменение данных о мероприятии по его уникальному идентификатору
- DELETE /events/{id} - удаление мероприятия по его уникальному идентификатору

<!-- NEW: описание модели события -->
## EventModel
- Guid Id - идентификатор мероприятия
- string Title - название мероприятия
- string Description - описание мероприятия
- DateTime StartAt - дата и время начала мероприятия
- DateTime EndAt - дата и время окончания мероприятия
- int TotalSeats - общее количество мест на мероприятии, задаётся при создании и не изменяется
- int AvailableSeats - количество свободных мест на текущий момент, уменьшается при создании бронирования, увеличивается при отклонении бронирования

# Метод получения списка всех мероприятий принимает следующие параметры
- title — регистронезависимый поиск по полному или частичному совпадению наименования мероприятия
- from — поиск мероприятий не раньше указанной даты
- to — поиск мероприятий не позже указанной даты
- page — разбитие списка мероприятий на страницы
- pageSize — количество мероприятий на странице

# Требования для запуска проекта

Для запуска приложения требуется:

- установленный .NET SDK;
- установленный и запущенный PostgreSQL.

Приложение использует PostgreSQL в качестве основной базы данных, поэтому перед запуском необходимо убедиться, что сервер PostgreSQL доступен.

# Настройка строки подключения к PostgreSQL

Строка подключения к PostgreSQL указывается в конфигурационном файле приложения.

Пример настройки строки подключения:

```json
{
  "ConnectionStrings": {
    "DefaultConnection": "Host=localhost;Port=5432;Database=eventapi;Username=postgres;Password=postgres"
  }
}
```
# Управление схемой базы данных

Схема базы данных управляется с помощью **миграций Entity Framework Core**.

Миграции позволяют фиксировать изменения модели данных в коде и последовательно применять их к базе данных. Это предпочтительный способ управления схемой БД в проекте.

## Создание миграции

Для создания новой миграции используйте команду:

```bash
dotnet ef migrations add InitialCreate --project EventManagerSystem
```

## Применение миграций к базе данных

Чтобы применить миграции к PostgreSQL, используйте команду:

```bash
dotnet ef database update --project EventManagerSystem
```

# Запуск и тестирование проекта

- Для того, чтобы выполнить сборку проекта, используйте команду:

```bash
dotnet build
```

- Для запуска проекта используйте команду:

```bash
dotnet run
```

Перед запуском убедитесь, что PostgreSQL запущен, а строка подключения настроена корректно.

При первом запуске схема базы данных будет создана автоматически через `EnsureCreated`.

- Для проведения тестирования используйте команду:

```bash
dotnet test
```

В тестах используется **InMemory-провайдер Entity Framework Core**, поэтому для запуска тестов не требуется подключение к PostgreSQL или отдельная тестовая база данных.

# 📅 Event Manager System - Booking Controller
- GET /bookings/{id} - получение бронирования по его уникальному идентификатору
- POST /events/{id}/book - создание бронирования для указанного мероприятия

## BookingModel
- Guid Id - идентификатор бронирования
- Guid EventId - идентификатор события
- BookingStatus Status - статус бронирования: Pending, Confirmed, Rejected
- DateTime CreatedAt - дата создания бронирования
- DateTime? ProcessedAt - дата изменения статуса бронирования

## Логика фоновой обработки бронирования
- Создаём бронирование на указанное событие
- Раз в 2 секунды `BookingProcessorService` проверяет наличие бронирований в статусе `Pending`
- Если были обнаружены такие бронирования, то `BookingProcessorService` получает полный список таких бронирований и с задержкой в 1 секунду изменяет статус на `Confirmed`

## 🔒 Синхронизация при конкурентном доступе

При создании бронирования несколько запросов могут одновременно обращаться к одному и тому же мероприятию и пытаться уменьшить `AvailableSeats`. Без синхронизации это приводит к **overbooking** — классическая проблема потерянных обновлений, когда два потока читают одно и то же значение `AvailableSeats`, независимо его уменьшают и перезаписывают, "затирая" изменения друг друга.

Для защиты используется **`SemaphoreSlim`** — по одному экземпляру на каждое мероприятие.

## Сценарий использования

Корректное создание бронирования — 202 Accepted

```json
{
  "id": "1dcfe5c5-369c-46d2-a55d-9fe7a0c7ab5f",
  "eventId": "59e4d8ec-f8ff-4dd8-b4d7-8bd78e69d532",
  "status": "Pending"
}
```

Получение созданного бронирования

```json
{
  "id": "1dcfe5c5-369c-46d2-a55d-9fe7a0c7ab5f",
  "status": "Confirmed",
  "processedAt": "2026-05-09T18:21:06.402831Z"
}
```

При попытке создать бронирование на несуществующее событие или получить несуществующее бронирование возвращается единый формат ошибки, описанный выше.

### ❌ HTTP 409 Conflict
Возвращается методом `POST /events/{id}/book`, если на мероприятии не осталось свободных мест (`AvailableSeats == 0`)

```json
{
  "status": 409,
  "detail": "No available seats for event 59e4d8ec-f8ff-4dd8-b4d7-8bd78e69d532"
}
```
